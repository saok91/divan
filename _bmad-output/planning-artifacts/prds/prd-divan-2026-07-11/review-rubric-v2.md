# PRD Quality Review — Divan HRIS (v2)

## Overall verdict
The revision materially improves the PRD: the Launch Artifact Register turns the former undifferentiated open-decision package into staged, owned, baseline-blocking contracts; the data-ownership contradiction is fixed; metric targets, Secondary Assignment scope, reservation trade-offs, and most policy placeholders now have named closure paths. It is close to launch-grade as a governing PRD, but not yet clean enough to approve unchanged: AR-NFR contains a high-impact timing contradiction that can move acceptance thresholds until production, while the new governance FRs introduce several narrower scope, terminology, mapping, and test-oracle ambiguities.

## Decision-readiness — adequate
The prior high finding that “core correctness remains behind an unclosed decision package” is substantially resolved by §8.1–§8.2: each decision family now has an owner, approvers, affected requirements, due stage, and an explicit rule that teams “MUST NOT substitute local assumptions.” The former data-owner timing contradiction is also resolved in §10, and FR-30 now surfaces and gates the operational cost of immediate Reservation.

The register is a strong contract for how decisions close, but it is not yet an operational register of which decisions have closed. More importantly, AR-NFR's wording conflicts with the stage rules and leaves a path for material targets to change after design and build.

### Findings
- **high** AR-NFR permits final thresholds after the gates that require exact values (§8.1 AR-NFR; §8.2; §9 NFR-2–NFR-13) — AR-NFR says “exact tests before build/acceptance; final thresholds and evidence before production,” while §8.2 requires “the exact matrix, values, formula/metric… before affected build” and says production sign-off “cannot cure a missed upstream gate.” NFR-2 likewise permits provisional 2/3/5-second targets until measured evidence supports alternatives. A test can be built against one bound and judged at production against another, making architecture and done-ness a moving target. *Fix:* Require every acceptance threshold and workload/environment bound to be approved and version-frozen before the earliest affected architecture, delivery, or feature baseline; reserve the production stage for evidence against that version, with any later threshold change governed as an impact-assessed rebaseline under FR-55.
- **medium** The Canonical Launch Artifact Register does not report current artifact state (§8.1; §11; §14) — The register defines artifact types and future timing but gives no current version, status, approval date, location, or explicit “not yet approved” state. A decision-maker cannot distinguish a missing artifact from an approved one without searching elsewhere, despite FR-55 requiring every item to be “versioned, attributable, approved for a stated scope and period.” *Fix:* Add current version/status/location/effective-expiry fields—or explicit `pending` entries—to each AR item, and require the PRD release to reference the exact artifact versions on which its readiness claim depends.

## Substance over theater — adequate
The added controls are mostly earned by the product's privacy, temporal, migration, and privileged-access risk. FR-46–FR-56 cover real failure modes—self-approval, stale authorization, inference leakage, unsafe spreadsheet artifacts, audit failure, retroactive report changes, and mixed-version operations—and the addendum adds concrete acceptance scenarios rather than generic security prose.

The main substantive overreach is the new definition of Data Element, which conflates governed element types with every concrete value and therefore makes “every Data Element” difficult to inventory or prove complete.

### Findings
- **medium** “Data Element” is defined at an unbounded value-instance level (§4 glossary; FR-7; FR-50; AR-DATA) — The glossary defines a Data Element as “any stored, free-text, metadata, inferred/derived, error, filter, or artifact value processed by Divan.” Read literally, every entered name, filter term, error string, generated cell, and metadata value is a separate Data Element, while AR-DATA is structured as a catalogue of fields/categories and FR-50 requires lifecycle rules for “every Data Element.” This makes completeness and acceptance unprovable. *Fix:* Define Data Element as a governed field, attribute, derived measure, metadata type, free-text class, filter parameter, error-data class, or artifact schema; state that concrete values inherit the governing element/classification and are tracked individually only where an FR explicitly requires instance evidence.

## Strategic coherence — strong
The product thesis still governs the capability set, and the new FRs reinforce rather than distract from trusted workforce state: authorization, retention, audit, report reproducibility, and snapshot integrity protect the same source-of-truth claim. The prior high success-metric finding is structurally resolved: §8 now requires AR-REPORTING to fix formulas, targets, windows, and remediation/stop conditions before the reporting/acceptance feature baseline, and missing values block that baseline rather than being deferred to launch. Actual target values remain an open artifact dependency, but the PRD now states the correct decision stage and consequence.

## Done-ness clarity — adequate
FR-46–FR-56 generally have observable consequences and named policy oracles, and the revised legacy FRs add useful race, idempotency, stale-reference, overlap, and fail-closed outcomes. The prior Secondary Assignment finding is resolved by FR-12 plus addendum §2.4's finite scenario and field inventory. Done-ness remains short of strong because one PRD/addendum conflict leaves import behavior with two incompatible acceptance outcomes, in addition to the high AR-NFR timing problem above.

### Findings
- **medium** Formula and active-content import handling conflicts across the PRD and addendum (FR-52; addendum §6.2) — FR-52 allows formulas, external links, and executable content to be “rejected or treated strictly as inert values,” while the addendum's mandatory safeguards say formulas, external links, macros, and executable/active content “are prohibited.” Because the addendum is non-authoritative, it cannot silently choose the stricter branch, and the combined phrase also treats harmless formula-looking text and executable workbook content as if they were one risk. *Fix:* State the authoritative per-content rule: reject workbook formulas/macros/external links and other active structures, define whether text beginning with formula characters is rejected or escaped as literal data, and bind acceptance fixtures to the selected behavior.

## Scope honesty — adequate
The original MVP boundaries remain explicit, and FR-53 carefully avoids employee self-service while FR-46 and FR-55 define bounded governance processes rather than a generic workflow engine. However, §7's scope summary was not updated to acknowledge the substantial new launch capabilities, and FR-53 leaves the boundary between case evidence and out-of-scope personnel document management unclear.

### Findings
- **medium** The MVP summary understates FR-46–FR-56 and leaves correction-case content on a scope boundary (§5.11; §6; §7.1; FR-53) — §7.1 still summarizes access, audit, reporting, migration, and operations in the older terms but does not name entitlement lifecycle, inference control, retention/legal hold, secure artifact lifecycle, data-subject correction cases, published-decision reproducibility, artifact change control, or snapshot integrity. FR-53 also requires “restricted supporting content,” while §6 excludes “Personnel document/file management unless separately approved,” without saying whether supporting content means references/metadata or stored files. *Fix:* Add the cross-cutting governance cluster to §7.1 and define FR-53's allowed evidence forms; if attachments are required, explicitly include the bounded correction-case artifact capability and exclude general personnel document management.

## Downstream usability — adequate
FR IDs are now contiguous through FR-56, the AR identifiers create much better extraction anchors, and the register's affected-requirement lists reduce the former “approved policy” ambiguity. Downstream teams can identify the required oracle for most features, but the new mapping is not complete enough to serve as a reliable traceability spine without manual inference.

### Findings
- **medium** New FR-to-artifact and launch-gate mappings have material omissions (§8.1; §8.3; FR-50, FR-53, FR-55) — AR-ACCESS does not list FR-50 or FR-53 even though retention operations and “restricted case evidence” require explicit action, category, and scope authorization; FR-53 names only AR-DATA despite requiring restricted content; and no hard launch gate explicitly states that it validates FR-55, even though every artifact and waiver depends on its change-control behavior. The broad default-deny FRs may imply coverage, but the register presents its `Affects` lists as the extraction contract. *Fix:* Add AR-ACCESS to FR-50/FR-53 where access and case permissions apply, map FR-53 to the exact restricted-case access/audit oracles, and explicitly include FR-55 acceptance in LG-6 (and any other gate that relies on artifact/waiver governance).

## Shape fit — strong
The document remains well-shaped for a chain-top enterprise HRIS. Named journeys establish operational use, capability groups hold the product contract, the new cross-cutting cluster contains enterprise controls that genuinely span domains, and implementation choices remain in the non-authoritative addendum. The added governance density is high but proportionate to sensitive workforce data, on-premise operations, migration risk, effective dating, and formal reporting.

## Mechanical notes
- FR IDs are contiguous and unique from FR-1 through FR-56; UJ-1–UJ-5 and SM-1–SM-6 remain contiguous, with SM-C1–SM-C5 clearly separated.
- AR-ACCESS, AR-TEMPORAL, AR-HEADCOUNT, AR-DATA, AR-IDENTITY, AR-AUDIT, AR-MIGRATION, AR-REPORTING, AR-NFR, AR-SECONDARY, and AR-CUTOVER are consistently named across the PRD and addendum.
- No inline `[ASSUMPTION]` tags appear, consistent with §15; the unknowns are instead indexed as staged artifact gates.
- Every UJ retains a named protagonist.
- Status vocabulary still alternates between action nouns (“Cancel/Reverse/Correction”) and result adjectives (“Cancelled/Reversed/Corrected”), but usage remains intelligible and should be fixed by AR-TEMPORAL rather than treated as a launch-grade defect in this PRD.
